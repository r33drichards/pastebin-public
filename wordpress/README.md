# WordPress PHP/MySQL pastebin

WordPress is the backend. The editor uses serialized HTTP autosave with retry and
unsaved-navigation protection. Other tabs do not synchronize; the last save wins.
WebSocket collaboration, presence, OT and the companion process are not part of
this deployment. Go language choices/examples are not removed with the Go backend. Experimental Go browser execution is separate from retiring the Go backend;
this change does not claim that a Go runner has been implemented.

## Install and routes

Requirements: WordPress 6.4+, PHP 8.1+ with DOM/libxml and mbstring, and WordPress's
MySQL driver with InnoDB/utf8mb4. Install `pbin/` as `wp-content/plugins/pbin/`.
Activation creates `{$wpdb->prefix}pbin_{pastes,diffs,snapshots,limits}`. Existing
production table names and the `pbin_schema_version` option are unchanged.

The default public editor is `/paste?id=UUID`. Visiting `/paste` or
`/paste?lang=lean` creates a new paste and returns a same-host 303 to `/paste?id=…`.
POST to `/paste` creates; PUT updates. IDs ending in `.txt` return raw text.
Other APIs live below the mount: `/paste/diff`, `/paste/snapshot`,
`/paste/snapshots`, `/paste/html`, `/paste/complete`, `/paste/health`, and
`/paste/static/*`. `/paste/paste` is not generated by canonical links.

Old `/pbin-wp-test/*` URLs remain same-data aliases. WordPress subdirectory
installations prefix both mounts with their home path. Home, blog, admin and REST
routes remain WordPress's. No rewrite flush is required. Remove any separately
configured `/paste` redirect only during the explicitly approved cutover.

Existing `PBIN_WP_BASE_PATH` configurations retain the old-style mount contract.
To configure the canonical editor explicitly, set `PBIN_WP_BASE_PATH='/paste'`
and `PBIN_WP_EDITOR_AT_BASE=true`. `PBIN_WP_ALIASES` optionally supplies an array
of legacy path aliases. Only a disposable test installation should use an empty
mount to expose the original root-level HTTP acceptance contract.

Deactivation stops routing but does not delete data. There is no automatic
uninstall purge or automatic migration of records from the former Go/Railway
database. That data cutover must be verified separately.

## Runtime and data

Paste, diff and immutable snapshots are stored in dedicated MySQL tables, not WP
posts or serialized PHP objects. Snapshot listing uses an indexed parent key.
The rate limiter has an instance-specific short-lived bucket table. Markdown is
sanitized; parser edge cases are not a claim of exact Go-renderer parity.
Completion and title providers are optional and disabled when unconfigured.
Preview instances ignore provider credentials.

The active PHP implementation lives in `Pbin\Plugin`; vendored Markdown classes
use `PbinVendor`. Templates are now authoritative source, not generated from Go
templates. Runtime assets are packaged with the plugin, including language choices
and existing WebAssembly runtimes. Runner browser tests remain required.

## Shared PR staging

See [preview/README.md](preview/README.md) for the trusted MU loader, immutable
SHA packages, per-PR URLs/table/options/storage isolation, lifecycle limits,
deployment transport gate and volume-safe rollback design. A single request
loads one package only. This is not a sandbox for untrusted PHP.

## Verification

Run `bash wordpress/ci/check-unit.sh` for the database-free checks. The portable
fixture in `wordpress/ci/run-fixture.sh` installs real WordPress against a
disposable local MySQL database and serves the exact supplied package for HTTP
and browser acceptance. Do not point it at a shared/production database.

Local unit tests cover mount boundaries, HTML/JS escaping, editor save/retry,
namespace/selector/asset/storage isolation, and deterministic package lifecycle.
They are not substitutes for the real WordPress/MySQL and runner-browser gates.
The current authoring sandbox cannot start server sockets, so those integration
gates have not yet run here. See CI output and staging evidence before promotion.

### Execution-origin release gate

Plugin-rendered documents are denied to signed-in WordPress sessions and fail
closed when authentication is unavailable. This is defense in depth, not a
sandbox: a guest runtime can outlive a later login. Production requires the
[execution-origin boundary and compatibility proof](../docs/wordpress-execution-boundary.md).
Use a separate browser profile without a WordPress login for current staging
runner checks; this testing precaution does not satisfy production isolation.
